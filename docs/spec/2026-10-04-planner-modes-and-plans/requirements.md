# 需求：量化计算模式扩展与生产方案管理

- 日期：2026-10-04
- 基线：commit `5007663`（已有 LP / 矩阵两种求解器，MCP 工具 `solve_production`、`machine_stats`、`production_matrix`）+ 项目结构重构（uv src 布局，`src/recipe_mcp/`）
- 相关文档：[design.md](design.md)、[tasks.md](tasks.md)

## 1. 背景

当前 `solve_production` 只支持"给定产出 → 求机器数"。实际规划（见工作区 `docs/` 下的甲醇效率、PC/ABS 与 PEX、塑料与绿板、绿瓶超市等规划文档）反复出现以下需求，目前只能靠一次性脚本（`analyze_methanol.py`、`analyze_pressure_transition.py`）或人工换算：

1. 原料、电力或已有机器受限时，最多能产多少，瓶颈在哪里。
2. 已有余料（乙烯、压缩氧气等）必须全部用掉时，能产多少。
3. 副产物排放需要多少烟囱 / 排水口，并计入设备数。
4. 一个工厂由多个模块组成，每个模块有自己的"外部接口"（边界投入/产出）；模块之间互相供料，需要整体汇总净输入输出。
5. 多轮调整同一方案（换插件、换机器、比较常压与加压路线），不应每次重发整套几十条产线配置。

调用方主要是 LLM（经 MCP），其次是 `recipe-mcp-cli` 命令行。

## 2. 目标与非目标

### 目标

- G1：在现有 LP 上增加**约束与最大化**类计算模式，并给出**瓶颈**与**不可行诊断**。
- G2：支持 Helmod 式**原料输入模式**（必须完全消耗给定输入），LP 与矩阵两种求解器都可用。
- G3：**副产物处置核算**：自动给出排放设备数量与耗电。
- G4：**生产方案持久化**：命名方案、多个块、增量编辑、版本冲突检测、过期检测。
- G5：**工厂级汇总**：块间供需抵消、净外部输入输出、块间目标联动。
- G6：不破坏现有工具的默认行为和返回字段（只增不改）。

### 非目标

- 图形界面、无限嵌套子块、拖拽排序、优先级 UI。
- 物流吞吐（传送带、管道、列车）、布局、蓝图生成。
- 品质、表面效果、流体矿衰减（沿用现有边界）。
- 自动跟随存档更新改写已保存的方案。
- 跨块的全局联合优化（所有块合并成一个 LP）：本期只做按块求解 + 汇总 + 联动。

## 3. 术语

| 术语 | 含义 |
|---|---|
| 产线（line） | 一个配方 + 机器 + 插件 + 信标配置；已在 `recipe_mcp.planner.model` 中实现 |
| 块（block） | 一次 `solve_production` 请求（目标、产线、模式、约束等）及其最近结果 |
| 方案（plan） | 命名的块集合 + 公共设置（队伍、时间单位），持久化为 JSON |
| 导入 / 溢出 | 块边界的外部输入 / 未被消耗的产出 |
| 消耗（consume） | 外部供给且必须**全部**被块消耗的物品数量 |
| 约束（limits） | 导入上限、电力上限、机器数上限、污染上限 |
| 缩放倍数 s | 最大化模式下的目标倍数：产出 = s × 比例 |
| 瓶颈 | 最优解处起作用（紧）的约束及其边际值 |

## 4. 用户故事与验收标准

优先级：**P0** 本期必须，**P1** 本期应做，**P2** 可延后。

### A. 计算模式

#### US-A1 原料 / 电力受限时的最大产量（P0）

> 作为玩家，我每秒只能供应 30 个石灰石、电网只剩 50 MW，想知道最多能产多少甲醇，以及先卡在哪一项。

验收标准：
1. WHEN `mode="maximize"` 且给出 `targets`（作为比例）与 `limits`，THEN 返回最大缩放倍数 `scale` 与按 `scale × 比例` 计算的完整结果（产线、机器、电力、导入、溢出）。
2. `limits.imports` 中列出的物品自动视为可导入，即使块内有生产配方。
3. `limits.power_MW` 约束全部电力机器与信标的平均耗电（与 `totals.power_MW` 口径一致）。
4. 结果中所有约束满足：`used ≤ limit + 1e-6`。
5. WHEN 最大化无界（没有任何约束限制产量），THEN 返回错误，提示需要哪类约束。
6. 在 `scale` 达到最大的前提下，再按 `objective` 最小化成本（两阶段），不会为了省机器而降低产量。

#### US-A2 多产物按比例（P0）

> 作为玩家，我要 6 种科技包按 1:1:1:1:1:1 生产，在当前原料下能做到多少。

验收标准：
1. `targets` 中多个物品的值作为比例，结果中各物品产出之比与输入比例一致（相对误差 < 1e-6）。
2. 比例中出现 0 或负数时报错。

#### US-A3 已有机器约束（P0）

> 作为玩家，我已经建好 8 台化工厂 2 和 4 台电解槽，想知道不新建设备能产多少。

验收标准：
1. `limits.machines_by_type: {机器名: 台数}` 限制该机器在所有产线上的小数机器数之和。
2. `limits.machines` 限制全部机器（不含处置设备）的小数机器数总和。
3. 未知机器名报错。
4. 已有的 `fixed_machines` / `max_machines`（单条产线）继续有效，可与本约束同时使用。

#### US-A4 原料输入 / 消耗余料（P0）

> 作为玩家，我有 35 压缩氧气/秒的余量（或大量乙烯余料），要求全部用掉，想知道配合哪些产线、能产出多少。

验收标准：
1. `consume: {物品: 速率}` 表示外部供给且**必须恰好全部消耗**；该物品在块内不再允许导入或溢出。
2. LP 下可与 `targets`（目标模式）或比例目标（最大化模式）组合。
3. 矩阵求解器支持 `consume`：此时 `targets` 可以为空，产出物品自动成为副产物未知量（Helmod 输入模式）。
4. 同一物品同时出现在 `consume` 与 `targets` 中时报错。
5. WHEN 无法完全消耗，THEN 不返回静默的部分解，而是走 US-A5 的不可行诊断，报告最多能消耗多少。
6. LP 自动发现产线时，若没有任何目标，则报错要求给出 `lines` 或比例目标（下游方向不自动探索）。

#### US-A5 不可行诊断（P0）

> 作为玩家，我要求 100 甲醇/秒但只给 30 MW，求解失败时我想知道差多少电，或者在 30 MW 下最多能做多少。

验收标准：
1. WHEN LP 在有 `limits` 或 `consume` 的情况下不可行，THEN 自动运行弹性松弛 LP，返回 `infeasibility`：每个被违反的约束、目标或消耗量的缺口（绝对值与相对比例）。
2. 错误信息包含可执行建议（"放宽 power_MW 至 ≥ X" / "目标最多可达 Y"）。
3. 没有约束时的不可行（例如缺少生产配方）保持现有报错。

#### US-A6 瓶颈报告（P0）

> 作为玩家，我想知道产量被哪项约束卡住，放宽 1 单位能多产多少。

验收标准：
1. 最大化模式返回 `bottlenecks`：所有紧约束，含 `limit`、`used`、`marginal`（放宽 1 单位约束带来的 `scale` 增量，单位换算到 `per`）。
2. 目标模式在有约束时返回紧约束及其边际成本（目标函数单位）。
3. 返回 `limits_usage`：每个约束的使用量与使用率，包括不紧的约束。
4. 整数模式（US-A8）不提供边际值，字段注明原因。

#### US-A7 副产物处置核算（P1）

> 作为玩家，我想知道多出的氧气、废水要几个烟囱 / 排水口，耗多少电，这些要计入设备数。

验收标准：
1. `disposal="report"`（默认）时，对每个溢出物品查找当前阶段可用的销毁配方（单一投入、无有效产出），按默认机器偏好选机器，返回 `disposal` 列表：物品、配方、机器、小数/取整台数、电力。
2. 处置设备单独汇总到 `disposal_totals`，不改动 `totals` 的现有口径；另给出 `totals_with_disposal`。
3. 找不到销毁配方的溢出物品列入 `disposal_unhandled`。
4. `disposal="none"` 时不计算。
5. 处置核算是事后计算，不影响 LP 的路线选择。

#### US-A8 整数机器数（P2）

> 作为玩家，规模很小时（每种 1–3 台）我想要真实可建的台数方案，而不是小数取整。

验收标准：
1. `integer_machines=true` 时机器数为整数决策变量，机器数约束与成本按整数台数计算。
2. 有 `time_limit`（默认 10 s）；超时返回当前最好解及 MIP gap，并标注。
3. 产线超过 400 条时拒绝，提示先用连续 LP 选路线、固定 `lines` 后再整数求解。

### B. 方案管理

#### US-B1 保存、列出、读取方案（P0）

> 作为玩家，我想把"10 甲醇/秒模块"保存为方案，下次直接调出来改。

验收标准：
1. `plan_save` 以名称创建方案；默认同名已存在时报错，`overwrite=true` 才替换。
2. 名称只允许 `[A-Za-z0-9_.-]`，长度 1–64，并拒绝 `.`、`..`；文件只能落在 `data/plans/` 下。
3. `plan_list` 返回名称、描述、块数、更新时间、修订号、过期状态。
4. `plan_get` 返回完整方案；`include_results=false` 时省略各块的上次结果。
5. 保存时校验每个块的请求能构建出产线（与 `solve_production` 同样的参数检查），失败时不写盘。

#### US-B2 增量编辑与冲突检测（P0）

> 作为玩家，我只想把甲醇产线的插件换成产能插件 2，不想重发整套配置。

验收标准：
1. `plan_edit` 接收操作列表，**原子**执行：任一操作失败则整个编辑不生效。
2. 支持的操作：添加/删除/重命名块，启用/停用块，合并修改块请求字段，添加/修改/删除产线（按产线 id），设置/删除目标，设置/删除约束与消耗，固定路线（US-B3）。
3. 每次成功写入修订号 +1；传入 `expected_revision` 且与当前不符时返回冲突错误，不写盘。
4. 写盘采用临时文件 + 原子替换，进程中断不产生半写文件。

#### US-B3 固定路线（P0）

> 作为玩家，LP 选好了路线，我想把它固定下来，之后只调插件 / 机器，不让求解器换配方。

验收标准：
1. `pin` 操作用该块最近一次 LP 结果的 `lines_for_matrix` 替换请求中的 `lines`，写入 `matrix_args`，并关闭自动发现。
2. 可选 `solver="matrix"`，固定后用矩阵求解器复算，结果与固定前 LP 的机器总数一致（相对误差 < 1e-6）。
3. 块没有上次结果时报错，提示先求解。

#### US-B4 多块工厂汇总（P0）

> 作为玩家，我的塑料工厂分为气体供应、PC/ABS 核心、PEX 三个模块，我想看整体对外需要什么、多出什么。

验收标准：
1. `plan_solve` 求解全部启用的块（或指定块），返回每块结果（默认摘要，`detail="full"` 返回完整结果）和工厂汇总。
2. 工厂汇总对每个物品计算：块输出（目标产出 + 溢出）、块输入（导入 + 消耗）、内部抵消量、净外部输入、净外部输出。
3. 汇总机器数、电力、污染、处置设备；处置需求按**净溢出**重新计算（块间供料后不再需要排放的不计）。
4. 明确声明假设：块之间视为共享总线，任一块的输出可供给任一块的输入，不建模物流。

#### US-B5 块间目标联动（P1）

> 作为玩家，我希望甲醇块的产量自动等于塑料块所需的甲醇，而不是我手算后填进去。

验收标准：
1. 块目标的值可以是数字，也可以是引用 `{"from": ["块id", ...], "plus": 数字}` 或 `{"from": "*"}`，表示等于这些块对该物品的导入量之和（`*` 为其他所有启用块），可再加 `plus`。
2. 按依赖拓扑顺序求解；出现循环时报错并列出循环路径。
3. 被引用的块未导入该物品时，该引用值为 0，并给出提示。
4. 求解结果记录每个引用目标的实际取值。

#### US-B6 过期检测（P0）

> 作为玩家，更新模组或重新导出存档后，我想知道哪些方案的数据已经过期。

验收标准：
1. 方案保存原型数据哈希、存档 tick 与存档副本哈希。
2. 读取、列出、求解时比较当前数据：原型哈希不同标记 `stale: "prototypes_changed"`；仅存档变化标记 `stage_changed`。
3. 过期不阻止求解（使用当前数据求解），但结果中带警告；不自动改写已保存的请求。
4. `plan_solve` 且 `save_results=true` 时更新块结果及其指纹，方案级指纹同步更新。

#### US-B7 方案 / 块对比（P2）

> 作为玩家，我想把常压与加压两个方案并排比较机器数、电力、原料、副产物。

验收标准：
1. `plan_compare` 接收两个"方案[/块]"引用，返回总量差值以及按物品的导入/溢出差值。
2. 使用已保存的结果；结果缺失或过期时提示先 `plan_solve`。

#### US-B8 安全删除（P1）

> 作为玩家，我误删方案时希望还能找回。

验收标准：
1. `plan_delete` 把文件移动到 `data/plans/.trash/<name>-<时间戳>.json`，不直接删除。
2. 必须传入 `confirm` 且等于方案名。
3. `plan_list` 不列出回收站内容。

## 5. 非功能需求

| 编号 | 要求 |
|---|---|
| NFR-1 兼容性 | 现有 14 个工具的参数默认值与返回字段不变；`tests/` 下原有测试全部继续通过 |
| NFR-2 性能 | 1000 条候选产线的连续 LP（含两阶段与弹性诊断）< 2 s；`plan_solve` 10 个块 < 5 s（Windows 本机，不含首次加载原型的约 1 s） |
| NFR-3 数值 | 平衡误差 < 1e-6；约束满足容差 1e-6；比例误差 < 1e-6 |
| NFR-4 安全 | 方案名白名单；只读写 `data/plans/`；单个方案文件 ≤ 1 MB；JSON 解析失败给出明确错误，不覆盖原文件 |
| NFR-5 可解释性 | 每个新增结果字段注明单位（`per` 换算后的速率、MW、台数）；所有诊断返回可执行建议 |
| NFR-6 可追溯 | 方案与结果都记录数据指纹与求解时间；不把过期结果当作当前结果返回 |
| NFR-7 依赖 | 不新增第三方依赖（scipy 1.18.1 已提供 `linprog` 对偶值与 `milp`，已在本机验证） |

## 6. 未决问题

1. **方案存放位置**：`data/plans/` 在 `.gitignore` 中（与其他导出数据一致，方案不进版本库）。若希望方案可提交，可改为 `plans/` 目录。**默认采用 `data/plans/`。**
2. **整数模式（US-A8）是否本期做**：默认列为 P2，排在 tasks 最后。
3. **跨块联合优化**：本期不做；若之后需要"所有块一起选路线"，可在 `plan_solve` 增加 `joint=true`，复用同一个 LP 构建器。
